## Машина и интерфейс
- Это вакуумная камера для литья силикона. Кинематическая схема: `uisketch.jpg` в корне.
- Три привода: стакан A, стакан B, шнек мешалки C.
- Стакан A содержит компонент A и вращается вокруг центральной оси. При наклоне компонент A переливается в стакан B, содержащий компонент B.
- Мешалка C погружена в стакан B и перемешивает компоненты.
- Стакан B вращается вокруг центральной оси; смесь переливается через воронку в литейную форму.
- Начальное положение стаканов соответствует скетчу, 0°. Рабочий диапазон — от 0° до 90° по часовой стрелке; против часовой — возвращение к 0°.
- У каждого стакана две отдельные кнопки: по часовой и против часовой. У мешалки одна кнопка включения/выключения вращения.
- Управление размещать рядом с соответствующим механизмом на схеме. Назначение приводов должно быть понятно по графике, без необходимости запоминать буквы A/B/C.
- При нажатии анимировать поворот стакана вокруг его центра; при работе C анимировать шнек. Воронка и форма неподвижны.
- Пользователь подтвердил: стаканы движутся только при удержании кнопки. Отпускание или отмена касания останавливает движение на текущем угле; на 0° и 90° движение ограничивается.
- Поворот стакана B при погружённой мешалке: механическая допустимость и необходимые блокировки не определены. Не выдумывать подъём мешалки или дополнительный привод.
- Интерфейс русскоязычный, рассчитан на мышь и сенсорный экран. Схема адаптируется к окну Windows и планшету, кнопки крупные.
- Демонстрационные углы — визуальная модель, а не подтверждённые положения реальных моторов. Явно показывать деморежим.

## Платформы
- Сначала Windows, затем Android с общим интерфейсом, анимацией и логикой на Dart.
- `androidsettings.jpg`: Android 7.1.1, API 25, обновление безопасности 1 июля 2018.
- `laptop.jpg`: планшет Lenovo TB-X304L. Не переносить IMEI и серийный номер в документацию или приложение.
- Android-сборка должна поддерживать API 25 и ARM32; проверять минимальные требования каждой зависимости. Android minSdk не выше 25.
- Windows-сборка выполняется на Windows с Flutter и Visual Studio C++ desktop tools. Linux-среда не может подтвердить Windows executable или реальное Bluetooth-подключение.
- Общий экран и модель не должны импортировать платформенные BLE API. Транспорт выделять отдельным интерфейсом.

## Связь с ESP32
- Пользователь выбрал Bluetooth. Существующая плата: ESP32-C3 DevKitM-1; текущая прошивка использует BLE GATT, не Bluetooth Classic/SPP.
- Существующий BLE service UUID: `6c8b5a90-7d2c-4c5e-98df-24a16d8a1001`.
- Write UUID: `6c8b5a91-7d2c-4c5e-98df-24a16d8a1001`; status UUID: `6c8b5a92-7d2c-4c5e-98df-24a16d8a1001`.
- Старые команды: `PING`, `RUN:<speed>:<reverse>:<revolutions>`, `STOP`. Они управляют одним мотором, не адресуют A/B/C.
- Новый протокол для трёх приводов необходимо согласовать и реализовать одновременно в приложении и прошивке. Не отправлять выдуманные команды старой прошивке.
- Новая схема подключения, GPIO, драйверы, редукция, калибровка и определение фактических углов пока не предоставлены.
- Реальное состояние и завершение движения должны приходить от контроллера. BLE write сам по себе не подтверждает физическое движение.
- Первый этап — работающий демоинтерфейс без отправки команд на оборудование; далее транспорт BLE Windows/Android и протокол v2.

## Проверка
- Для автоматической подготовки локального Windows и запуска следовать `WINDOWS_HANDOFF.md`; сценарии — `scripts/setup-windows.ps1` и `scripts/build-windows.ps1`.
- Проверенный SDK исходников: Flutter 3.47.7 / Dart 3.13.5. Windows SDK устанавливать отдельно от Linux/WSL SDK.
- Для приложения запускать `flutter analyze` и `flutter test`.
- Проверять ограничение углов, независимость приводов, запуск/останов мешалки, останов анимаций и отсутствие переполнения интерфейса на разных размерах.
- Не заявлять проверку реального оборудования или готовую Windows/Android-сборку без фактического запуска соответствующих проверок.
